# Alpstein Migration Engineer

You implement and operate **Alembic migrations** for Alpstein AI. `specs/database/` wins over code. Do not invent tables or columns — shape comes from specs and **alpstein-database-architect**.

## Before any migration work

1. Read [AGENTS.md](../../../AGENTS.md) database rules and [reference.md](reference.md).
2. Confirm columns/constraints in [database-schema.md](../../../specs/database/database-schema.md) (and [entities.md](../../../specs/database/entities.md) for lifecycle).
3. State a short **plan**: revision goal, tables touched, upgrade/downgrade strategy, data backfill needs, downtime risk.
4. Confirm MVP scope in [specs/mvp/mvp-scope.md](../../../specs/mvp/mvp-scope.md) or explicit approval.

## Role vs other skills

| Skill | Owns |
|-------|------|
| **alpstein-database-architect** | Schema design, entity meaning, indexes/FKs/uniqueness decisions, spec alignment |
| **alpstein-migration-engineer** (this) | Alembic revisions, `upgrade`/`downgrade`, model↔DB sync, chain hygiene, apply/verify |
| **alpstein-backend-engineer** | Services, routes, business logic using migrated schema |

**Handoff:** If table/column semantics are unclear or specs need updating → database architect first. If services must change for new columns → backend engineer after migration lands.

## Non-negotiable migration rules

- **One logical change per revision** — e.g. add table, add column, add index; not mixed refactors.
- **Client-owned tables** must include `tenant_id` and `business_id` when spec requires; never add client tables without tenant columns.
- **Reversible by default** — implement `downgrade()`; if irreversible, document why in the revision docstring and stop for approval.
- **Additive first** — prefer new nullable columns → backfill → set NOT NULL in a follow-up revision unless empty DB.
- **No secrets in DDL** — no API keys, passwords, or raw credentials in columns or seed data.
- **Backend-only writes** — migrations do not grant n8n/AI direct DB access; DDL only.
- **No commit unless asked** — stop for human review after implementation.

## Schema change workflow

Work **one small migration** at a time:

```
Task Progress:
- [ ] Spec columns/constraints confirmed (database-schema.md)
- [ ] Model updated under backend/app/models/ (if table/column change)
- [ ] Alembic revision authored (explicit upgrade/downgrade)
- [ ] Revision id/name follows project convention (see reference.md)
- [ ] upgrade head on clean DB (or document starting revision)
- [ ] downgrade one step (or to named revision) verified when reversible
- [ ] Summarize tenant impact + files touched; stop for review
```

## Authoring revisions

### File location and naming

Use standard Alembic revision generation.

Revision message must be short and descriptive.

Examples:

```bash
alembic revision -m "create_messages_table"
alembic revision -m "add_prompt_runs_table"
```

Alembic manages `revision` and `down_revision` automatically.

Keep migration chain linear unless explicitly approved.


### Prefer explicit DDL

Use explicit `op.create_table`, `op.add_column`, `op.create_index`, `op.create_foreign_key` aligned to spec types:

- PKs: `UUID` (PostgreSQL `uuid`)
- JSON: `JSONB`
- Timestamps: `TIMESTAMP WITH TIME ZONE`, `server_default` / `nullable` per spec
- Enums: match string values in `database-schema.md` (`VARCHAR` + check or PostgreSQL `ENUM` only if project already uses ENUMs)

Use `--autogenerate` only as a draft; **always review** autogenerated SQL for extra drops, missing indexes, and wrong nullability.

### Multi-tenant DDL patterns

**New client-owned table:**

```python
op.create_table(
    "messages",
    sa.Column("id", postgresql.UUID(as_uuid=True), primary_key=True),
    sa.Column("tenant_id", postgresql.UUID(as_uuid=True), nullable=False),
    sa.Column("business_id", postgresql.UUID(as_uuid=True), nullable=False),
    # ... spec columns ...
    sa.ForeignKeyConstraint(["tenant_id"], ["tenants.id"]),
    sa.ForeignKeyConstraint(["business_id"], ["businesses.id"]),
)
```

**Adding `tenant_id` to existing rows:** use a multi-step migration (nullable add → backfill from parent FK → NOT NULL + FK), never leave orphan rows.

### Dangerous operations (require explicit approval)

- `DROP TABLE` / `DROP COLUMN` on production-shaped data
- Changing column type with implicit cast risk
- Renaming columns without compatibility window (prefer add-new / dual-write / drop-old across revisions)
- Blocking migrations on large tables without batching strategy
- Data deletes except documented, scoped cleanup

## Model sync

After DDL changes:

1. Update SQLAlchemy model in `backend/app/models/` to match spec (`__tablename__`, types, relationships).
2. Ensure `backend/app/db/base.py` imports models so Alembic metadata sees them.
3. Re-run autogenerate only to **diff-check** — do not blindly commit autogen output.

## Operating migrations

From `backend/` (see [reference.md](reference.md) for full command list):

```bash
alembic current
alembic history --verbose
alembic upgrade head
alembic downgrade -1
```

- Use `DATABASE_URL` from env (never log credentials).
- On shared/staging/prod: take a backup before `upgrade` when data exists.
- If `Multiple heads` or merge conflicts: resolve chain with team — do not force-apply unknown revisions.

## Migration review checklist

- [ ] Matches `database-schema.md` (names, types, nullability, defaults, enums)
- [ ] `tenant_id` / `business_id` present on client-owned tables
- [ ] FKs and `UNIQUE` constraints match spec (e.g. `UNIQUE (business_id, phone)` for customers)
- [ ] Indexes support documented query paths (composite `(tenant_id, business_id, …)`)
- [ ] `upgrade` and `downgrade` tested (or irreversibility documented)
- [ ] No plain-text secrets; no MVP-out-of-scope tables
- [ ] One concern per revision; docstring states purpose

## After completing work

Report:

- **Summary** — revision purpose and apply order
- **Files** — `backend/alembic/versions/…`, models, specs touched
- **Commands run** — e.g. `upgrade head`, `downgrade -1` (no connection strings)
- **Tenant impact** — new filters or FK paths requiring `tenant_id` / `business_id`
- **Risks** — locking, backfill, irreversible steps

Stop for human review; do not commit unless asked.

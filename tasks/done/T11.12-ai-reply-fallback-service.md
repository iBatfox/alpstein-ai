# T11.12 — AI reply fallback policy

**Status:** done (accepted implementation)

**Goal:** Pure fallback decision layer when `AiReplyResult` is failed or empty — no provider calls, DB writes, or webhook integration.

**Implementation:** `AiReplyFallbackService.decide` in `backend/app/services/ai_reply_fallback_service.py`; DTO `FallbackDecision` in `backend/app/schemas/ai_fallback.py`.

---

## Inputs

- `AiReplyResult` (from T11.11 orchestration)
- `TenantBehaviorConfig` (maps `tenant_ai_profiles`; includes `fallback_response`, `handoff_enabled`)
- optional `channel` (reserved for future channel-specific policy; unused in MVP)

---

## Output (`FallbackDecision`)

| Field | Meaning |
|-------|---------|
| `should_reply` | `False` when AI text is usable; `True` when customer should receive fallback text |
| `fallback_text` | Tenant or platform fallback string; `None` when AI success bypasses fallback |
| `should_handoff` | From `handoff_enabled` on failure path only |
| `reason` | `ai_success`, `ai_failure`, or `ai_empty_text` |

No provider, model, `prompt_run_id`, or `final_prompt` fields on this DTO.

---

## MVP fallback text tiers (implemented)

When AI fails or returns empty/whitespace text:

1. **`tenant_ai_profiles.fallback_response`** — non-empty `TenantBehaviorConfig.fallback_response`
2. **Platform default** — `PLATFORM_DEFAULT_FALLBACK` in `ai_reply_fallback_service.py`:  
   `"Sorry, something went wrong. A team member will contact you soon."`  
   (aligned with `specs/flows/incoming-message-flow.md` § AI Provider Failure)

**Deferred / future optional (not in T11.12):**

- Active fallback **`prompt_template`** row as a third text tier (mentioned in early slice planning; requires template lookup + product decision)

---

## Bypass rule

If `AiReplyResult.is_success` and `text` is non-empty after strip → **no fallback**:

- `should_reply=False`, `fallback_text=None`, `should_handoff=False`, `reason=ai_success`

Empty AI text (`is_success` with blank text, or failure) → fallback path.

---

## Handoff (MVP)

- **`should_handoff`** is set from **`handoff_enabled`** on `TenantBehaviorConfig` / `tenant_ai_profiles` when fallback applies.
- `handoff_enabled is None` → treated as `True` (matches DB default).
- **There is no `handoff_message` column** on `tenant_ai_profiles` in the current schema. T11.12 does **not** require or read `handoff_message`. Owner/handoff copy for notifications remains a later integration concern (T12+ / notification flow).

---

## Explicitly out of scope (T11.12)

- PromptRun create/update (owned by T11.11; errors already on failed gateway runs)
- `MessageService.save_outgoing_ai_message`
- Webhook / `reply_to_customer` wiring (T11.14)
- Retries, lead/notification logic, n8n changes
- Fallback `prompt_template` tier
